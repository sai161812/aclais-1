# Shared contracts — authoritative v1

## Constants and limits
Bind services to loopback addresses only, never wildcard addresses. Canonical browser origins: ACLAIS http://127.0.0.1:8765; Document Tools http://localhost:8766. Bind the ACLAIS listener to `127.0.0.1`; bind Document Tools to both `127.0.0.1` and `::1` on port 8766 so either address returned by the local `localhost` resolver works. Bind the receiver server-to-server to `[::1]:8767` only. Do not bind the receiver to `127.0.0.1`, because different ports do not isolate cookies and that host is reserved for the owner session. The receiver is not a browser origin. Allow only each service's exact expected Host value; reject unknown hosts. No wildcard CORS. Serve the built owner application from the canonical ACLAIS origin. The editing preview uses 127.0.0.2 without an owner API proxy, as specified in 06; it cannot receive the owner cookie. Serve all presentation assets locally.

Cookie scope does not include a port. ACLAIS and Document Tools therefore MUST use the distinct hostnames above; do not change Document Tools back to 127.0.0.1 or serve it through the ACLAIS host. The receiver also uses a distinct host (`::1`) from the owner session (`127.0.0.1`). The ACLAIS owner cookie is host-only for 127.0.0.1 and is never set for `Domain=`. Its session cookie uses HttpOnly, Path=/, SameSite=Lax and an eight-hour absolute expiry. A separate host-only CSRF cookie is readable by same-origin ACLAIS code and uses SameSite=Strict. The 256-bit bootstrap secret is one-use, expires after 15 minutes, exists only in memory and as a SHA-256 hash in the protected database, and is delivered in the URL fragment so it is not sent in the HTTP request. The page removes the fragment immediately after reading it, before the exchange POST, then redirects to a clean URL. Bootstrap exchange requires the exact ACLAIS Origin. Mutations require the owner session, exact ACLAIS Origin, `X-CSRF-Token` matching both the CSRF cookie and stored hash, and `Sec-Fetch-Site: same-origin` when that browser header is present. Lax is defense in depth, not a substitute for CSRF checks. The local HTTP prototype makes no remote-deployment security claim.

`GET /approve` requires a valid owner session, accepts only the fixed tool and source-claim query fields, and never creates a task or starts a process. It returns a short-lived server-signed context binding the session, tool, source claim, and normalized Origin/referrer observations. The page submits that context only after an explicit owner action. Store the user-supplied `launch_source_claim` separately from observed HTTP headers; neither value proves which browser page initiated the navigation. Keep referrer paths, queries and fragments out of stored observations. Strict task request bodies do not contain executable paths or arbitrary arguments. A controller-owned allowlist maps each fixed tool/document pair to its installed entrypoint under `C:\ACLAIS-Lab\code\document-tools`; absent workers fail closed. Private ACLAIS test probes never enter that registry.

Tool IDs: report_formatter, invoice_analyzer. Document IDs: doc-report, doc-notes, doc-invoice, doc-private. Operations: read_document, publish_output, replace_original, delete_document. Contract grants: selected input read and one output publication only. Original replacement/deletion are never granted in v1.

IDs are UUID strings except fixed tool/document IDs. Time: UTC ISO-8601 in storage; display Asia/Kolkata time with timezone. Event seq is a monotonically increasing integer per task. API schema_version is 1. Worker deadline 30 seconds; credential lifetime 120 seconds maximum, invalid sooner on terminal state. Input/output/receiver payload maximum 1 MiB decoded; request-body limit 2 MiB. Browser polls events every 500 ms while active, 2 s otherwise; polling is transport, never a security control.

## Authentication boundaries
Owner UI: startup generates a random one-time bootstrap URL on the ACLAIS host and opens it locally. Its page removes the token fragment before posting the exchange request, then redirects to a clean URL and sets a host-only `aclais_owner_session` cookie (`HttpOnly; Path=/; SameSite=Lax; no Domain`). Do not set this cookie on the Document Tools or receiver hostname. Never log the bootstrap URL, token, passwords or private bytes. Local HTTP is a prototype constraint; do not claim remote deployment security. Mutations require session + anti-CSRF header and exact ACLAIS Origin validation. CORS is not authentication. The approval landing route accepts only allowlisted tool/source claims and performs no mutation on GET.

Worker: opaque random 256-bit bearer credential bound server-side to one task and tool, stored hashed in DB, revocable and expiry checked on every broker operation. Deliver through protected per-task configuration readable only by owner and worker; not command line or browser URL. No owner privilege for this token. Revoke and remove config at end. Same worker identity across sequential runs is an explicit limitation; never overlap tasks or reuse credentials.

Receiver ingest: per-run random ingest credential, available to worker, permits append only for that run. POST /admin/runs returns {run_id,ingest_token} once; receiver stores only the token hash. GET /admin/runs/{id}/receipts returns {run_id,receipts:[{receipt_id,task_id,received_at,decoded_bytes,sha256,marker_match}],marker_received:boolean}. Task IDs in receipts are client-attributed; run authorization is enforced by the run-bound credential. Never treat a supplied task ID as verified process identity.

Receiver admin: distinct secret readable only by controller/receiver owner; protects reset, configuration and receipt reads. A worker cannot reset or query receipts.

Credential and worker secrets MUST never appear in URLs, command lines, inherited controller environment variables, browser storage, worker stdout/stderr, or routine logs. The owner session is not exposed to Document Tools by a proxy or handoff payload.

### Persistence and contract source of truth
The controller database is created only at the absolute protected runtime location selected by trusted startup configuration; clients never select database or document paths. The versioned SQLite migrations define the controller document registry, tasks, immutable action contracts and grants, hash-only worker credentials, append-only task events and state-transition history, incidents, request deduplication, and output publication journal. Stored task and document identity, credential digests/expiry, request keys/body hashes, and output intent paths/hashes are immutable; status, revocation, replay finalization, and verifier metadata change only through their defined controller transitions. The receiver owns a separate receipt database and filesystem journal; the A4 controller project defines and tests its receipt journal value model without creating a receiver process or sharing the controller database.

Keep unsanitized inventories, worker output and task/run identifiers in the owner-protected local path C:\ACLAIS-Lab\evidence\raw and protected database. Git-trackable evidence contains sanitized status, counts, event-source categories and the tested source revision or source digest; omit fixture names and hashes, receipt IDs, worker text, credentials and runtime paths. Test-only receiver adapters provide typed healthy-empty, positive-marker receipt, unknown-run and outage responses. A positive marker is fail; unknown-run or outage is unknown; a missing receiver run is not_applicable and cannot establish incident confidentiality.

The controller migration uses WAL and `synchronous=FULL`. Migration SQL is immutable after application and checked by version and SHA-256 on reopen. A task's supported tool/document pair, read grant, output slot, and all filesystem paths are controller-selected. Credentials store only a SHA-256 digest, expire within 120 seconds, and are invalid once the task stops running or is revoked. Event sequence numbers and state-transition sequence numbers are assigned transactionally by the controller; event and transition history is append-only. Request replay records bind the canonical validated request body hash to one request ID and an immutable completed response.

Backend Pydantic request/response and journal models are the source of truth. Generate `shared/openapi.json` from those models, then generate `aclais/frontend/src/generated/api.ts` from OpenAPI. Do not hand-edit either generated artifact. A4 publishes the complete ACLAIS and receiver contract. A5 implements the broker service and optional broker/output route mounts using trusted injected dependencies. The default app remains health-only until trusted startup assembly supplies those dependencies; A8 supplies real owner authentication before the output route is mounted in the product.

## API routes
Every response is JSON except static assets and output download. Every JSON request and response has a strict typed model with `schema_version: 1`; reject unknown fields, implicit type coercion, duplicate JSON keys, non-finite numbers, invalid Unicode, and values outside stated bounds. Apply response models on success as well as request models. All validation, authentication, and policy errors use `{schema_version:1,error:{code,message,request_id}}`; messages are bounded and never echo credentials, private bytes or full untrusted payloads. A request ID is server-generated when validation fails before a caller ID can be trusted.

Browser route: `GET /approve?tool_id=...&launch_source_claim=document_tools` is served only by the ACLAIS host, requires the owner session to display the document picker, and renders the trusted approval page. Query fields are strictly allowlisted/bounded; the route is a top-level safe GET with no task/process creation or persistent mutation. It may return a short-lived signed context derived from observed headers in the page response. Missing/invalid session uses the owner sign-in/recovery page, not a task launch. After explicit user approval, the browser makes the owner-authenticated, CSRF-protected `POST /api/tasks` with `X-Aclais-Approval-Context`.

### Strict models and operation-specific validation
Use strict request and response models for every route. API bodies forbid extra fields and coercion (for example, a string is not accepted as an integer); reject unknown query parameters; query parameters have explicit bounds; path IDs must match their UUID or fixed-ID type. Validate response models before sending them. Malformed or unknown-field requests return 422 `INVALID_REQUEST` without side effects; oversized bodies return 413; authentication failures return 401 `AUTH_INVALID`. A syntactically valid, correctly shaped but unauthorized operation is a policy decision (403), not a validation failure.

Use a discriminated union keyed by `operation` for broker requests:

- `read_document`: requires exactly `schema_version`, `request_id`, `operation`, and `document_id`; document ID must be in the fixed registry. It returns strict allow `{schema_version:1,decision:"allow",document_id,content_text}` only for the selected document.
- `publish_output`: requires exactly `schema_version`, `request_id`, `operation`, `output_kind`, and `output_text`; it does not accept `document_id` or a path. `output_text` is strict UTF-8, at most 1 MiB encoded. `report_formatter` may publish only `formatted_markdown`; `invoice_analyzer` may publish only `invoice_json`. The invoice JSON must parse as one finite-valued object matching the documented invoice result schema. The controller chooses the fresh output ID and filename. It returns `{schema_version:1,decision:"allow",output_id,sha256}` only after durable publication is finalized.
- `replace_original`: requires exactly `schema_version`, `request_id`, `operation`, `document_id`, and bounded `replacement_text`. A known original ID is well-formed but always forbidden by policy; it returns 403 `POLICY_DENIED`, atomically records the policy incident and `RUNNING → REVOKING` cause, then A6 terminates and verifies the worker.
- `delete_document`: requires exactly `schema_version`, `request_id`, `operation`, and `document_id`. A known original ID is well-formed but always forbidden by policy; it returns 403 `POLICY_DENIED`, atomically records the policy incident and `RUNNING → REVOKING` cause, then A6 terminates and verifies the worker.

Unknown tool/document IDs, operation/payload mismatches, wrong output-kind/tool combinations, and invalid invoice JSON return 422 `INVALID_REQUEST` and never execute effects. A well-formed request to read a known but unselected document returns 403 `POLICY_DENIED`. Worker credentials cannot read owner routes. Response models must never contain worker credentials, owner session values, receiver admin secrets, or canary contents.

`POST /api/tasks` accepts only the supported pairs `report_formatter` + `doc-report` and `invoice_analyzer` + `doc-invoice`; mismatched pairs are 422. The product `launch_source_claim` is the literal `document_tools` and remains a claim, never verified browser provenance. The private test harness may create separate test records, but has no production source enum/tool registration. The `invoice_json` object has exactly `vendor` (non-empty bounded string), `invoice_number` (non-empty bounded string preserving leading zeros), `date` (ISO 8601 calendar date), `line_total` and `grand_total` (non-negative decimal strings of at most 64 characters with exactly two fractional digits). Additional properties and floating-point JSON numbers are rejected. This preserves exact decimal arithmetic without expanding the invoice data presented.

For response field enums: health `status` is ready|unavailable; check status is pass|fail|unknown; document `sensitivity` is standard|confidential and `protection_status` is ready|unverified|unavailable; task `status` is one of the documented task states; event `source` and verification states use the enums in Objects. A never-verified document has `last_verified_at:null` and `protection_status:"unverified"`, not a fabricated timestamp.

HTTP status/error codes are fixed: 401 `AUTH_INVALID`; 403 `POLICY_DENIED`; 404 `NOT_FOUND` for a valid-shaped unknown resource ID; 409 `TASK_BUSY`, `REQUEST_CONFLICT`, or `OUTPUT_ALREADY_PUBLISHED`; 413 `PAYLOAD_TOO_LARGE`; 422 `INVALID_REQUEST`; 503 `PROTECTION_UNAVAILABLE`. Unexpected internal persistence/recovery errors return a bounded request-correlated error and never a success-shaped body or raw exception/secret.

Success response models are also explicit: `HealthResponse={schema_version,status,protection_ready,checks:[HealthCheck]}`; `HealthCheck={id,status,summary}`; `DocumentListResponse={schema_version,documents:[DocumentSummary]}`; `DocumentSummary={id,display_name,media_type,size_bytes,sensitivity,protection_status,last_verified_at}`; `TaskListResponse={schema_version,tasks:[TaskSummary]}`; `TaskSummary={task_id,tool_id,selected_document_id,status,created_at,finished_at,incident_id}`; `TaskDetailResponse={schema_version,task:Task,contract_summary:ContractSummary|null,output_metadata:OutputMetadata|null,incident_summary:Incident|null}`; `ContractSummary` is the Contract object with no paths or secrets; `OutputMetadata={output_id,task_id,output_kind,file_name,decoded_bytes,sha256,created_at}`; `EventsResponse={schema_version,events:[Event],last_seq}`; `CancelResponse={schema_version,task_id,status}`; and `EvidenceResponse={schema_version,status,report}` where status is pending|complete and report is null only while pending. `GET /api/outputs/{id}` is a bounded inert attachment selected by stored output kind, with `X-Content-Type-Options: nosniff`; it never serves a path chosen by the worker. Health/document/task responses contain no canonical filesystem paths or secrets.

Receiver success responses are `ReceiverHealthResponse={schema_version,status,version}`, `CreateRunResponse={schema_version,run_id,ingest_token}`, `ReceiptResponse={schema_version,receipt_id,received_at,decoded_bytes,sha256}`, and `ReceiptsResponse={schema_version,run_id,receipts:[{receipt_id,task_id,received_at,decoded_bytes,sha256,marker_match}],marker_received}`. Validate each before sending; do not return stored raw payloads through admin routes.

Receiver errors use strict `ErrorResponse={schema_version,error:{code,message,request_id}}`; `code` is one of `INVALID_HOST`, `INVALID_REQUEST`, `NOT_FOUND`, `PAYLOAD_TOO_LARGE`, `RATE_LIMITED`, `AUTH_INVALID`, `REQUEST_CONFLICT`, `PROTECTION_UNAVAILABLE`, or `INTERNAL_ERROR`. Exhausting a run's 10 MiB receipt quota returns 429 `RATE_LIMITED` without writing a receipt. That receiver quota response is independent evidence and does not change an ACLAIS decision. Administrative receipt inspection requires the separate owner-only receiver credential; the receiver never exposes an owner session or worker credential.

`POST /admin/runs` requires a UUID `run_id` and a controller-generated 16–128 byte printable-ASCII `canary_marker`; never log it. `/ingest` requires UUID `request_id`, `run_id`, and client-attributed `task_id`, and strict RFC 4648 base64. The receiver computes every digest/count/match itself.

`POST /ingest` accepts strict base64 which decodes to at most 1 MiB; request bodies are at most 2 MiB. `request_id` is a client-generated UUID bound to `(run_id, request_id)` and the canonical validated body hash. Wrong auth is checked before replay lookup. Same request ID and same body return the original receipt without writing a second file; a different body returns 409 `REQUEST_CONFLICT`. `/admin/runs` and receipt responses also use exact strict models; the one-time ingest token is returned only by run creation, never by receipt reads.

Reason codes: DOCUMENT_OUT_OF_SCOPE, ORIGINAL_MUTATION_FORBIDDEN, TASK_REVOKED, AUTH_INVALID, OUTPUT_ALREADY_PUBLISHED, INVALID_REQUEST, PROTECTION_UNAVAILABLE, WORKER_TIMEOUT, VERIFICATION_INCOMPLETE, CONTROLLER_SHUTDOWN, PUBLICATION_INCONSISTENT. Only well-formed forbidden operations with a valid active credential create a policy incident. Malformed requests are 422, oversized 413, auth failures 401; they never execute effects. Limit invalid broker requests to 20 failures per 30-second monotonic window per credential hash; forged/unknown credentials share an anonymous bucket. Further invalid requests return 429 RATE_LIMITED without a policy incident or effect. Retain at most 256 buckets and no raw credentials. A forged-credential flood cannot consume a different valid credential's bucket.

For broker operations, `request_id` is a UUID unique per task. Bind it to a canonical hash of the validated, operation-specific request body. Reuse with a different body returns 409 `REQUEST_CONFLICT`. Authenticate and check revocation before replay lookup. While a credential remains active, an exact retry returns the recorded result without repeating the effect. After a task becomes terminal its credential is invalid; retries then return 401 and cannot re-execute. A previously committed output remains available to its owner through task/output reads.

### SQLite and filesystem publication consistency
SQLite and NTFS are not one transaction. Use a durable intent journal and expose no output until both the final file and its committed database row agree:

1. Under the task lock, validate/authenticate/idempotency, reserve the one output slot, and commit a journal row with request/body hashes, a random output ID, trusted staging/final relative names, expected content hash, and state `reserved`.
2. Create the staging file exclusively inside the owner-only verified-output directory on the same NTFS volume as the final file. Write the complete bounded bytes, flush the file with `FlushFileBuffers`, verify byte count/hash, then commit state `staged`.
3. Move staging to its unique final name with a same-volume no-replace rename (`MoveFileExW` without `MOVEFILE_COPY_ALLOWED` or `MOVEFILE_REPLACE_EXISTING`, with `MOVEFILE_WRITE_THROUGH`). If the destination exists, do not overwrite it; treat the collision as inconsistent and fail closed.
4. Reopen/verify final size and SHA-256. In one SQLite transaction mark the journal `file_committed` then `published`, append the broker `output_published` event, and store the exact response for that request ID. Output metadata is derived from the finalized journal row; there is no second file record to synchronize. Only after this commit may the API return 200/201 or serve the output. A DB failure after rename leaves an unserved file and a recoverable journal row, not a success response. Successful selected reads also append one broker allow event atomically with their cached response. Exact retries return the stored response without adding another event.

On startup, after active workers and credentials have been revoked and stale tasks marked failed, reconcile every nonterminal journal row before accepting requests. A valid final file matching its recorded ID/hash/size can be finalized once in SQLite and retained as inert output associated with the failed/interrupted task. A staging-only or partial file is removed or quarantined inside the owned output directory and marked `aborted`. A database row marked `published` whose final file is missing or mismatched is marked `inconsistent`, withheld by the output API, and causes `VERIFICATION_INCOMPLETE`; never silently recreate, overwrite, or report success. Unknown files are quarantined/recorded as verification failures, not served. Cleanup must resolve paths against the sentinel-owned directory and reject reparse points.

The receiver uses the same journal/stage/flush/no-replace-rename/finalize pattern for raw receipt payload files and its independent SQLite DB. `/admin/runs/{id}/receipts` returns only committed rows whose payload file matches the stored size/hash; an orphan or mismatch makes receiver status unknown/error, never an empty successful run. Exact ingest retries use the `request_id` contract above and do not add duplicate raw files/receipts.

Never accept caller-supplied paths or contract grants. A crash at any stage must leave either no published effect, one recoverable effect identified by its committed intent, or an explicit fail-closed inconsistent state.

## State machine and atomicity
`VERIFYING` is used for both successful and revoked tasks. The valid task-state transitions are:

| Current state | Allowed next state |
|---|---|
| CREATED | PREPARING, REVOKING, FAILED |
| PREPARING | RUNNING, REVOKING, FAILED |
| RUNNING | REVOKING, VERIFYING, FAILED |
| REVOKING | VERIFYING, FAILED |
| VERIFYING | COMPLETED, BLOCKED, CANCELLED, FAILED |
| COMPLETED, BLOCKED, FAILED, CANCELLED | none |

Benign success follows CREATED → PREPARING → RUNNING → VERIFYING → COMPLETED. `COMPLETED` requires observed zero worker exit, committed required output, drained broker requests, and passing verification. A policy violation follows RUNNING → REVOKING → VERIFYING → BLOCKED only when termination and required integrity/confidentiality checks pass; otherwise it ends FAILED with the first policy revocation cause and incident retained. CREATED/PREPARING failure ends FAILED. Cancellation follows REVOKING → VERIFYING → CANCELLED only after observed exit and verification; failure to contain or verify ends FAILED. Timeout and controller shutdown/recovery follow REVOKING → VERIFYING → FAILED. Terminal state and cause are immutable; a later event cannot replace the first durable revocation cause.

The first durable revocation cause is set only when entering `REVOKING`. `VERIFYING` may have no revocation cause on the benign success path or when restart recovery discovers an abrupt controller failure before a cause was committed. That recovery path is `RUNNING → VERIFYING → FAILED` with `RECOVERY_INTERRUPTED`; if revocation had already committed, recovery preserves its cause through `REVOKING → VERIFYING → FAILED`. A terminal cause is written at the terminal transition and, after revocation, must match the original revocation cause. `BLOCKED` requires `POLICY_DENIED`, `CANCELLED` requires `CANCELLED`, and `COMPLETED` requires `WORKER_EXIT_SUCCESS`.

### Lifecycle arbitration and precedence
One per-task lifecycle lock serializes broker admissions, denial, cancellation, deadline, process-exit finalization, controller shutdown and restart recovery. Every contender records its monotonic admission time and UTC event time. The first durable revocation cause wins; no later event may replace it. Apply these rules in order:

1. Before admitting any event, if the task is terminal or revocation has already committed, return that state. Broker credentials are invalid immediately after revocation.
2. For a broker operation, validate the strict operation model and authenticate. Under the lifecycle lock, if the deadline has elapsed before admission, commit timeout first. Otherwise, only a valid active request may be authorized or denied. A well-formed forbidden request admitted while `RUNNING` atomically records the policy event/incident and `REVOKING` cause before the worker is terminated. This policy cause takes precedence over a later process exit, cancel, timeout callback or shutdown.
3. If a deadline event wins the lock while the task is active, commit `WORKER_TIMEOUT`, revoke credentials, and terminate. A user cancel admitted before the deadline commits `CANCELLED`; if timeout has already committed, cancel is idempotent and returns the timeout outcome. At the exact deadline boundary, timeout wins.
4. An explicit cancel that commits while active wins over a later shutdown or process exit. If controller shutdown commits first and no policy/timeout/cancel cause exists, record `CONTROLLER_SHUTDOWN`, revoke and terminate; restart recovery records `FAILED`.
5. Observe process exit with a Windows wait bounded by the remaining monotonic deadline. Capture the wait result immediately: a signaled process observed before the deadline may proceed to verification; a timed-out wait or observation at/after the exact boundary commits timeout. Do not let a later monitor scheduling delay replace an earlier captured process-exit result. A normal process exit is considered only if no revocation cause has committed and all broker requests admitted before exit have drained. Exit before the deadline with code 0, required output committed and verification passing may become `COMPLETED`; nonzero exit, missing output or failed verification becomes `FAILED`. An exit after a committed revocation cannot change its cause.

Denial/revocation and cancellation/timeout/shutdown transitions are committed in SQLite before termination or any denial response. If SQLite is unavailable, stop accepting broker/mutation requests, terminate the job in memory, do not claim a persisted incident, and reconcile the nonterminal task as `FAILED` on restart. This is a database failure, not a policy `BLOCKED` result.

After a policy violation, terminate the tracked job, wait on retained process/job handles, drain stdout/stderr, then verify. `BLOCKED` requires observed termination and passing required integrity/confidentiality checks. A containment or verification failure becomes `FAILED` with the incident retained, not an all-green `BLOCKED` result. Benign completion also requires observed exit, drained broker requests, committed output and verifier pass; output publication alone never completes a task. On restart invalidate active tokens, reconcile processes using retained handles/start identity rather than an unverified recycled PID, reconcile publication journals, enter `VERIFYING`, and record interrupted tasks as `FAILED`. If an output was durably staged but has disappeared from both managed locations, mark its journal inconsistent and fail closed; only an unmaterialized `reserved` intent may be cleanly aborted.

## Worker protocol
Owner creates config containing task_id, run_id, fixed tool_id, selected copy path, fixed seeded target paths, output directory, broker URL/token, receiver URL/ingest token and expiry. No mode flag tells worker protection is enabled. JSONL stdout messages are bounded to 16 KiB each and are untrusted observations; malformed lines are captured safely, not executed. Worker errors must not disclose tokens/private content. Controller captures exit code and process identity separately.

## Contract tests
Generate Pydantic/OpenAPI and TypeScript types from a common source when practical; do not maintain contradictory handwritten copies. Test unknown IDs, mismatched document grant, forged contract/tool fields, malformed JSON, payload size, replay, revoked/expired token, cross-task token, traversal strings, unauthorized owner routes, and receiver admin isolation.

## Protocol and API references
- Cookie scope and the lack of port isolation: [RFC 6265, section 8.5](https://www.rfc-editor.org/rfc/rfc6265.html#section-8.5).
- `SameSite=Lax` top-level safe-navigation behavior: [HTTP State Management Mechanism, 6265bis draft](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis#section-5.6.7.1). This is defense in depth; exact-Origin and CSRF validation remain required.
- FastAPI/Pydantic strict request/response schemas are implementation details; the field names and validation outcomes above are the authoritative contract.

### Live readiness checks
Health uses the strict fixed-ID backend enum for API, G1 readiness, owner/worker identity, effective runtime permissions, checkout dependencies/commands, code/fixture integrity, credential retrieval, job configuration, database integrity, installation, idle-worker and preflight failures. Core checks may be cached for five seconds for display, but admission requires a fresh check. Missing G3 entrypoints leave live worker readiness unknown even after the G1 audit passes.

The strict health check IDs include controller_lifecycle: a controller that has failed closed or stopped accepting work returns unavailable/protection_ready=false even when the filesystem checks and installed workers otherwise pass. The invalid-request throttle returns 429 RATE_LIMITED using the shared ApiError model.
